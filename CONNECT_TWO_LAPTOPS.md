# Как соединить бэкенд и ИИ на двух ноутбуках

Для первого запуска подключите оба ноутбука к одной обычной Wi-Fi-сети.
Бэкенд и его worker работают на ноутбуке коллеги; ИИ работает на ноутбуке Султана.
Worker передаёт аудиофайл и метаданные по HTTP, получает JSON и сохраняет результат
в базе бэкенда. Общая папка и перенос PostgreSQL на ноутбук с ИИ не нужны.

Пример ниже: **ноутбук с ИИ — 192.168.1.50**, порт **8000**.
Этот адрес приведён для примера: замените его своим IPv4 из `ipconfig`.
Бэкенд в инструкции запускается на порту **8080**.

## 1. Сначала обновите проекты

Распакуйте обновлённый архив бэкенда на ноутбуке коллеги.
Перенесите в него рабочий `backend/.env` и сохраните прежние `DATABASE_URL` и
`STORAGE_DIR`: они должны указывать на его существующую базу и папку записей.
Обновлённый архив ИИ содержит пояснения по запуску; код моделей и API не менялся.
Уже работающий ИИ можно оставить в его текущей папке, сохранив `.env` и модели.

Все команды ниже — для PowerShell. Python: 3.11 или 3.12.
Если виртуальное окружение уже есть, повторно создавать его не нужно.

## 2. На ноутбуке с ИИ

Узнайте адрес:

```powershell
ipconfig
```

Нужен IPv4 активного Wi-Fi/Ethernet-адаптера, доступного второму ноутбуку.
Адреса Docker/WSL/VirtualBox для этого примера не подходят.

### Если ИИ уже работает через Docker

Перейдите в папку `hack-bdffe61d-exit-1-ai/ai-service`.
В её `.env` проверьте `AI_PORT=8000`. Сохраните рабочие настройки моделей и `AI_MODE=real`,
если реальное распознавание у вас уже настроено.

```powershell
docker compose up -d
curl.exe http://127.0.0.1:8000/health
```

В исходном `docker-compose.yml` порт ИИ уже опубликован на хосте.
Если запускали с дополнительным GPU-файлом, используйте свою прежнюю команду Compose
с обоими файлами. При смене переменных `.env` примените её снова.

### Если запускаете через Python

В папке `ai-service`:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Если `.env` отсутствует, создайте его:

```powershell
Copy-Item .env.example .env
```

Для первичной проверки транспорта используйте в `ai-service/.env`:

```dotenv
AI_MODE=mock
INTERNAL_TOKEN=
```

Запустите сервис и оставьте окно открытым:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --env-file .env --host 0.0.0.0 --port 8000
```

`--env-file .env` обязателен для чтения файла настроек при таком запуске.
Сам `Settings.from_env()` читает только окружение процесса.
Файл с именем `env` в корне старого архива автоматически не загружается.

В другом окне:

```powershell
curl.exe http://127.0.0.1:8000/health
```

Ожидается `{"status":"ok","mode":"mock"}` либо `mode: real` для настроенных моделей.
`mock` проверяет передачу данных и возвращает заранее заданный текст.

Для реального распознавания оставьте/настройте `AI_MODE=real`, ML-зависимости,
локальные веса Whisper/pyannote и модель Ollama по README ИИ.
При запуске вне Docker `OLLAMA_URL` обычно равен `http://127.0.0.1:11434`,
а `MODEL_DIR` должен указывать на вашу настоящую папку моделей.
Одна установка `requirements.txt` не устанавливает ML-модели и не включает распознавание.

## 3. На ноутбуке с бэкендом: проверить сеть

Подставьте IPv4 ноутбука с ИИ:

```powershell
Test-NetConnection 192.168.1.50 -Port 8000
curl.exe http://192.168.1.50:8000/health
```

Продолжайте, когда `TcpTestSucceeded: True` и `/health` возвращает JSON ИИ.
`localhost` или `127.0.0.1` на ноутбуке коллеги указывают на ноутбук коллеги.
В `AI_BASE_URL` нужен адрес ноутбука Султана.

Если локальная проверка ИИ работает, а удалённая — нет, проверьте:

- ИИ слушает `0.0.0.0:8000`, окно процесса открыто.
- Оба устройства находятся в одной сети; гостевая Wi-Fi-сеть может изолировать клиентов.
- Брандмауэр разрешает входящий TCP 8000 на ноутбуке с ИИ.

При необходимости для доверенной частной сети Windows выполните на ноутбуке с ИИ
в PowerShell от администратора:

```powershell
New-NetFirewallRule -DisplayName "Hackalem AI 8000" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 8000 -Profile Private -RemoteAddress LocalSubnet
```

Правило действует для профиля «Частная сеть». Не отключайте брандмауэр целиком.

## 4. На ноутбуке с бэкендом: настроить HTTP-клиент

В `backend/.env` сохраните существующие настройки PostgreSQL/хранилища и добавьте:

```dotenv
AI_MODE=http
AI_BASE_URL=http://192.168.1.50:8000
AI_INTERNAL_TOKEN=
AI_TIMEOUT_SECONDS=3600
FRONTEND_ORIGIN=http://localhost:5173
```

`AI_BASE_URL` указывается без `/internal/process` — клиент добавляет путь сам.
Если на ИИ выставлен другой `AI_PORT`, укажите именно опубликованный порт.

Для включённой проверки токена значения должны совпадать:

| Где | Переменная |
|---|---|
| Ноутбук с ИИ, `ai-service/.env` | `INTERNAL_TOKEN` |
| Ноутбук с бэкендом, `backend/.env` | `AI_INTERNAL_TOKEN` |

Можно сгенерировать общий токен командой `python -c "import secrets; print(secrets.token_urlsafe(32))"`
и вписать результат в оба файла. Пустые значения на обеих сторонах отключают эту проверку.
После изменения настроек перезапустите ИИ, API и worker, которых затронули изменения.

В папке `backend`:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m app.check_ai
```

Для миграций PostgreSQL должен быть запущен, база и пользователь из `DATABASE_URL` должны существовать.
`app.check_ai` проверяет доступность и режим ИИ; проверка `/health` не проверяет токен.
Проверить также токен и передачу настоящей записи можно так:

```powershell
.\.venv\Scripts\python.exe -m app.check_ai --audio "C:\audio\meeting.wav"
```

Эта команда обрабатывает запись напрямую через ИИ и не создаёт совещание в базе.
В реальном режиме дождитесь завершения обработки.

Режимы не путать:

| `AI_MODE` бэкенда | `AI_MODE` ИИ | Результат |
|---|---|---|
| `mock` | любой | Встроенная заглушка бэкенда, сетевого запроса нет |
| `http` | `mock` | Реальный HTTP-запрос, ответ-заглушка от ИИ |
| `http` | `real` | Реальный HTTP-запрос и распознавание моделями |

В бэкенде `real` также принят как синоним `http`; рекомендуем `http`, чтобы различать настройки.

## 5. Запустить API и worker — два окна на ноутбуке бэкенда

Первое окно, из папки `backend`:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 0.0.0.0 --port 8080
```

Второе окно, из той же папки `backend`:

```powershell
.\.venv\Scripts\python.exe -m app.worker
```

Оба процесса используют один `backend/.env`. API сохраняет файл и ставит задачу в очередь;
worker отправляет его в ИИ. Без worker совещание останется в `queued`.
Для ноутбука с ограниченной памятью запускайте один worker.

Откройте Swagger бэкенда: `http://127.0.0.1:8080/docs`.
`GET /ready` проверяет подключение бэкенда к PostgreSQL.

## 6. Проверить весь путь до протокола

В третьем окне из папки `backend` подставьте путь к своей записи:

```powershell
.\.venv\Scripts\python.exe scripts/smoke_e2e.py --audio "C:\audio\meeting.wav"
```

Скрипт создаёт тестовое совещание в вашей базе, загружает запись и ждёт worker.
Ожидается `queued` → `running` → `completed` (быстрые промежуточные статусы могут не попасть в вывод).
После завершения он скачивает `test-protocol.docx` в текущую папку.
В режиме ИИ `mock` внутри будет демонстрационный текст, а не содержимое вашей записи.

Проверить вручную можно в Swagger:

1. `POST /meetings`: поля `file`, `title`, `started_at`, `timezone`, `participants_json`.
2. Для `started_at` — дата с часовым поясом, например `2026-09-23T17:00:00+05:00`.
3. Для `timezone` — `Asia/Almaty`; для `participants_json` — `[{"name":"Султан"},{"name":"Даурен"}]`.
4. `GET /meetings/{id}` — дождаться `completed`.
5. `GET /meetings/{id}/export?format=docx` — получить протокол.

В сетевом режиме доступны WAV, MP3 и M4A. WEBM/OGG/MP4 нужно заранее преобразовать:
ваш текущий ИИ-сервис принимает только эти три формата. Бэкенд теперь сообщает об этом до постановки в очередь.

Если фронтенд находится на третьем устройстве, его API URL должен указывать на
`http://IP_БЭКЕНДА:8080`; `FRONTEND_ORIGIN` бэкенда должен совпадать с адресом и портом страницы в браузере.
HTTP-связь бэкенда с ИИ не зависит от CORS. Фронтенда в присланных архивах нет.

## Если ноутбуки в разных сетях

Адрес `192.168.x.x` из чужой локальной сети напрямую не доступен.
Для первого демо подключите оба устройства к одной сети. Другой вариант — общая
частная VPN-сеть с маршрутом между ноутбуками: в `AI_BASE_URL` укажите VPN-адрес ноутбука с ИИ
и разрешите порт 8000 для адреса второго ноутбука на соответствующем интерфейсе.
Приведённое выше правило `LocalSubnet/Private` может не подходить для VPN-интерфейса.

## Если не заработало

| Симптом | Что проверить |
|---|---|
| Нет ответа от `/health` со второго ноутбука | IPv4, порт, `0.0.0.0`, брандмауэр, изоляция Wi-Fi |
| `/health` отвечает, но обработка даёт 401 | Совпадают ли два токена; перезапущены ли процессы |
| Совещание остаётся `queued` | Запущен ли `python -m app.worker`, одинаковы ли его база и настройки API |
| Долго стоит `running` | Логи ИИ; реальное распознавание на CPU может идти долго |
| `failed` с ошибкой аудио | Действительный WAV/MP3/M4A, непустой файл, размер в лимитах обоих сервисов |
| ИИ вернул демонстрационную презентацию | Проверьте `AI_MODE`: сначала бэкенд `http`, затем ИИ `real` |
| Сработал таймаут | Логи моделей; увеличьте `AI_TIMEOUT_SECONDS`, затем перезапустите worker |

Автоматического повтора упавших задач здесь нет. После исправления причины создайте
новое совещание и загрузите файл заново. Если процесс worker был принудительно завершён,
его старая задача может остаться `running`; автоматического восстановления таких задач пока нет.

## Что изменено и что проверено

Добавлены HTTP-клиент с передачей файла/JSON, токен и настраиваемый таймаут,
преобразование формата ИИ в формат бэкенда, передача имён участников и локальной даты,
диагностика соединения, проверочный сценарий до DOCX и понятные сетевые ошибки.
Записи о неизвестных исполнителях, сроках или фрагментах помечаются для проверки.
Структура PostgreSQL не изменялась.

Проверено в среде разработки: **15 новых тестов бэкенда и 16 существующих тестов ИИ**.
Сквозной тест использует отдельный процесс вашего ИИ-сервиса по настоящему HTTP
в `mock`-режиме; сохранение результата и экспорт проверены с временной SQLite-базой.
PostgreSQL, Windows-брандмауэр, сеть между вашими ноутбуками и реальное ML-распознавание
в этой среде не проверялись — для этого выше приведён `smoke_e2e.py`.

Таймаут ожидания ответа настроен отдельно от 10-секундного установления соединения;
поведение описано в [документации HTTPX](https://www.python-httpx.org/advanced/timeouts/).
